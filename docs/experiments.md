# Keenly 实验记录

每次改动后追加一条。格式：**改了什么 → 指标怎么变 → 为什么**。
只记有数据支撑的结论，不记猜测。

---

## 1 — GPU vs CPU 门禁的舍入底噪（2026-11-11）

**现象**：`keenly --check` 首跑 relL2 = 1.36e-05，超了随手定的 1e-5 预算。

**实验**：同一份代码，关掉 `--use_fast_math` 重测 → relL2 降到 6.15e-06。
说明底噪来源是 fast-math 的近似除法 + FMA 收缩（host/device 编译路径不同），
不是 bug——真实管线 bug 的量级在 1e-2 以上。

**教训**：verify 门禁的阈值要由实测底噪和真实 bug 量级共同决定，不能拍脑袋。
「relL2 必须是 0」在浮点世界是伪命题——当时是这么以为的，见实验 3。

## 2 — 舍入底噪随运算链长度增长（2026-11-11）

**改动**：quality 轮把 fieldPixel 从 3 次 field 求值加到 5 次（双尺度浮雕），
fBm 每 octave 加 4 次旋转乘加。

**现象**：门禁 relL2 从 1.36e-05 涨到 **6.5e-05**，接近当时 1e-4 的预算。

**分析**：FMA 收缩的舍入差是逐级累积的——运算链越长，CPU/GPU 的差异越大。
这不是代码质量问题，是预算模型太粗（只考虑了单点底噪）。

**教训**：门禁预算要为「未来更长的运算链」留余量，并且把测得的底噪机制
写进代码注释——否则每个后来者都要重新做一遍实验 1。

## 3 — 换 IEEE 数学，门禁升级为位级全等（2026-11-11）

**现象**：新增 bands 生成器（warpField 的三角波等值线）门禁直接失败：
relL2 = 2.6e-3、maxAbs = 6.9e-2，远超 2e-4 预算。frost 模式同时只差 9e-7。

**分析**：不是索引 bug。bands 的 fold 把上游浮点差逐级放大：×12 频率 →
折叠分支切换 → sstep 斜率 1.875 → 调色板 smoothstep 斜率 ~7.5，总增益约
126 倍。实验 2 的「预算随链长增长」模型挡不住这种**结构性增益**。

**解法**：改用严格 IEEE 数学（`--fmad=false`、不加 fast-math）。实测：
**全部生成器 relL2 = 0.000e+00、maxAbs = 0.000e+00**。

**决定**：门禁从「relL2 < 预算」收紧为「maxAbs == 0」，并作为项目铁律写进
CMake 注释。位级全等是最强的正确性声明，而且不再需要任何预算模型——
预算那套复杂度是 fast-math 的税。

**教训**：与其不断给误差预算打补丁，不如换一个让误差为零的编译约定。
「艺术渲染不在乎 1% 速度，在乎可复现」——性能 flag 是 per-target 的事。

## 4 — 用直方图抓「太平」的生成器（2026-11-11）

**现象**：新 liquid 生成器首版统计难看：亮度值域塌缩在 [0.06, 0.67]，
57% 的像素挤在同一个 octile——「液态金属」渲染成了灰色果冻。

**诊断**：不是 bug，是两个设计问题：(1) warpField 值域钟形集中，×0.9
后更窄，调色板两端根本够不到；(2) 高光是乘性的，palette 中间色 ×2 也
到不了白——而金属反射本质是**加性光**。

**修复**：场强 ×1.30；高光拆成乘性宽高光（powi 16）+ 加性白 glint
（偏暖，模拟钨丝反射）。复测：std 0.088 → 0.212，值域 [0.02, 0.89]，
高光 octile 占比 15%。

**教训**：生成器调完要看**直方图形状**，不只看均值方差：值域塌缩和
双峰分布是两种完全不同的「对」。prism 的双峰（31% 暗 / 28% 亮）正是
「凛冽」的量化特征。
